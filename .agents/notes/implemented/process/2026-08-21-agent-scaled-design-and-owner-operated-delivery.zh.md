# Agent Note: 面向多智能体的设计与个人负责的交付

Status: implemented

[English](2026-08-21-agent-scaled-design-and-owner-operated-delivery.md) | 中文

## 问题

多个编码 agent（智能体）可能并行修改本仓库，因此它们需要稳定的所有权、依赖关系和单一真相来源规则。但集成与发布由个人负责：一位维护者在本地验证改动后发布。把传统大型团队的完整清单同时套在这两件事上，会把有用的架构约束与目前没有实际负责人或发布需要的评审角色、环境晋级、发布流程和固定指标混在一起。

通用架构清单还会脱离仓库现有的 plugin（插件）模型，指定固定的分层、模式、文件行数和抽象。这样可能在 Cordis 旁边造出第二套架构，而文件行数本身不能证明一个文件承担了多项职责。

## 决策

仓库架构和距离改动位置最近的 `AGENTS.md` 优先于通用模式。模块围绕一个明确归属的变更原因保持高内聚。跨模块依赖使用已有且适合该关系的类型化 service（服务）、事件或公开 API；不得穿透实现细节或引入循环依赖。只有实际领域或仓库架构需要时，才使用 DDD、传统应用分层、事件、接口、工厂等模式。

实现从最小、直接的方案开始。抽象、选项、共享辅助函数或扩展点必须对应当前消费方、已经观察到的变化，或者确实具有同一归属的重复知识。领域规则、类型、配置和文档各自只保留一个权威来源。归属不同的相似代码不自动构成重复。

源码文件超过 500 行时检查职责，而不是自动拆分。生成文件、声明式目录和职责内聚的测试可以更长。拆分必须形成真实的所有权或依赖关系边界。性能工作先保证正确，再根据测量到的瓶颈开展，而不是为预想规模提前优化。

架构和文档保持足够显式，以支持多个 agent 并行工作。交付仍由个人负责：改动保持小而可逆，Git 记录恢复点，维护者只在能够证明改动行为的最小范围本地检查通过后发布。不可逆的数据操作或外部副作用需要预先准备备份或回滚方案。人工评审、额外 CI/CD 阶段、环境逐级晋升、灰度发布以及固定的覆盖率或技术债比例都不是默认要求；已有仓库规则或具体发布风险仍可要求这些措施。

## 考虑过的替代方案

**原样采用完整的大型团队清单。** 否决，因为固定分层、文件行数、覆盖率比例、评审角色和发布阶段并非由本仓库架构或个人负责的发布流程推导而来。这份清单会增加流程负担，还可能与约束更强的仓库专用规则冲突。

**只保留现有的仓库专用规则。** 否决，因为 agent 还需要简短的通用规则，判断职责、依赖方向、抽象门槛和文件大小信号，并区分并行实现与个人负责的发布。

**立即重构所有大文件。** 否决，因为文件长度只是检索成本信号。只有具体改动暴露出可以独立归属的职责，并且能够验证拆分结果时，才调整现有实现。

## 结果

agent 共享稳定的决策规则，无需再引入第二套架构。新改动沿用现有扩展点，并且只根据证据建立抽象。大文件会进入重点检查，而不是被机械改写。

维护者保留简短的本地发布循环，同时继续遵守仓库质量门禁和由风险决定的回滚要求。只有真实团队、外部义务或发布风险为团队式交付控制提供当前用途时，才增加这些控制。
