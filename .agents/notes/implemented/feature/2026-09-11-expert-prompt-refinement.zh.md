# Agent Note: 专家提示词优化

Status: implemented

[English](2026-09-11-expert-prompt-refinement.md) | 中文

## 问题

一次对话可以证明某条局部提示词指令有问题：用户先修正回答，后续回答再展示更好的行为。如果这项经验只留在对话记录里，下次对话无法使用；如果仅凭一个例子重写完整提示词，又可能破坏无关行为。

用户还需要检查并拒绝模型提出的提示词修改。自动写入会把概率性的解释当成已经接受的配置，也不会留下“哪些文字发生了变化”的稳定记录。

## 决策

专家在内部使用受管的聊天模式 agent preset。它的目录包含受管组装、`expert.json`，以及 `versions/` 下不可变的编号提示词与变更记录文件。创建流程会为 preset 分配一个不显示的稳定标识符，不要求用户填写目录名。专家提示词是其 Session 的完整 persona；欢迎语只属于浏览器文案，绝不进入模型历史。公开 Agent 模式名单会排除专家，专家名单只在聊天模式内部展示。受管组装使用聊天模式的 shell 与文件系统工具，挂载时也会为旧版本写入的专家恢复这份组装。

既有 `agent-presets` 服务负责专家发现、创建、编辑、版本冲突与优化。专家选择复用既有的空白 Session preset 切换。浏览器向编辑器菜单贡献可搜索的专家选择器，并复用既有右侧栏完成管理、子 Agent 进度、对比、编辑与确认。选择器按「专家列表」、「新增专家」、专家行排序；每个专家行把版本放在名字旁边，并把编辑固定在最右侧作为次操作。字段与已提交文档相同时，「保存专家」保持禁用；保存期间字段会被锁定，成功后显示「已保存」，直到再次编辑。明确进入管理页面会清除该 Session 在浏览器中保存的优化状态，请求标识会阻止延迟返回的优化结果重新打开对比页面。

优化是 Host 拥有的进程内一次性子 Agent。它完整运行既有 `standard` preset，继承当前 Session 选择的模型路线，并收到一条显式调用随附 `expert-prompt-refiner` skill 的精简中文用户消息，该 skill 注册在已发布的子 Agent 自身作用域上，而不是部署级目录。协调器不会额外设置 persona、请求大小、输出 token、重试或截止时间，因此标准组装和模型路线会保留对所有运行时能力与执行策略的决定权（[决策](../bug-fix/2026-09-12-expert-refinement-standard-inheritance.zh.md)）。中文 skill 要求同时存在明确修正和后续改好结果，只修改证据支持的最小提示词条款，并且只调用一次既有 `structured_output` 工具。它保持提示词原语言，同时用简体中文填写 summary 与 reason。子 Session 会记录普通 Agent 事件、skill 注入与工具活动；Host 校验捕获的每个字段，并在内存中保存候选稿。

候选稿不会写入任何文件。浏览器复用既有对话视图展示不带输入框的子 Session：专家面板申请 `conversation.view` 的只读 `fixedSessionSlots` 权限，renderer 提供固定 binding 视图，不转移声明所有权，也不产生跨插件运行时 import。子级会收到一条用于触发 skill 的精简用户任务，以及位于其前方、由插件提供的 `promptContext`；后者包含完整专家系统提示词，以及已配置的近期证据窗口，其中只有用户输入与助手最终文本答案。助手 reasoning 块和内嵌 reasoning stream 记录保留在来源 Session 中，绝不会进入优化上下文。注入上下文通过既有的折叠“上下文注入”行显示；优化子级自身的思考则保留普通的实时单行折叠摘要。运行标题栏的停止操作通过 RPC signal 中断正在启动的请求，或撤销并释放已经发布的子级。面板随后左右呈现完整的旧提示词与建议提示词。建议提示词可以编辑，确认会把这份检查后的文本提交给 Host 保存的提案。确认要求基础版本仍是当前版本，并追加一个不可变版本。保存修改后的提示词或确认候选稿，会为目标专家 Session 的后续请求安装 agent 局部的完整提示词覆盖；其他已打开 Session 保持各自版本。每条历史记录都会按需读取该版本及紧邻的上一版，在同一个左右高亮界面中只读展示；只改元数据不会生成历史记录。提示词应用事件让恢复后的 Session 重建所选覆盖。新专家 Session 读取已提交的当前版本。普通分支会保留所选对话前缀，但在发布前应用专家当前版本，因此文本不同时，下一次请求会记录既有的系统提示词更新。过期编辑器或旧 Session 会收到版本冲突，不会合并或覆盖更新的提示词。

## 考虑过的替代方案

**新建独立专家插件和 Session 类型。** 否决，因为 agent preset 已经负责逐 Session 组装、独立目录、发现、选择与生命周期。平行的专家注册表会让“Session 到底运行哪份提示词”出现两个权威。

**在聊天模式里挂载普通 skill 目录。** 否决，因为专家对话需要文件处理，而不是标准 skill 目录。独立的 `standard` 子级只在优化运行中提供既有 skill loader 与完整工具展示；专家对话只接收聊天模式的文件工具，不提供 skill 发现。

**不创建 Agent Session，直接调用模型。** 否决，因为私有 stream 需要另一套进度协议与渲染器，还会隐藏既有 Session 与对话视图已经能展示的 skill 注入、思考和工具事件。

**让对话模型自动重写自己的提示词。** 否决，因为对话输出无法证明每一种泛化都值得接受。可检查候选稿与显式确认让人继续掌握配置修改权。

**只保存最新提示词。** 否决，因为左右对比和后续排查都需要不可变的来源版本，以及每次确认时的准确修改理由。

## 后果

专家在组装与 Session 重建方面使用普通 agent-preset 机制，但产品界面只通过专家端点列出它们。已归档的[逐 Session preset 决策](../../archived/architecture/2026-08-03-per-session-agent-presets.md)与[聊天文件能力决策](2026-09-11-chat-file-capabilities.zh.md)分别负责这些机制。

子 Agent 只在用户主动优化时增加一次独立的 `standard` preset 模型运行。它的完整输入、skill 注入与输出都位于子 Session，不进入父级对话。保存或确认版本会修改目标 Session 的提示词前缀，因此提供方缓存复用会从该提示词重新开始。其他已打开 Session 保持自己已经安装的提示词；新 Session 与普通分支使用已提交的当前版本，恢复的 Session 则重建自己最后应用的版本。

版本文件只追加，并且仅保存在本地用户根目录。当前指针与展示元数据使用原子替换，每次更新都会检查预期版本。两个编辑器可以同时读取，但同一版本只能由第一个写入者提交成功。
